# 铁路隐患对象与 AI 后果建模提示词

## 1. 目的与边界

本提示词用于把原平台的铁路危险货物运输隐患评估记录，映射为数字站场中的**定性演示情景**。输入来自平台已有评估记录和《铁路危险货物运输隐患排查治理动态评估体系》参考表，不要求操作人员重复录入。

AI 输出的是“结构化后果建议 + 现有程序化场景分支 + 现场弹幕”，由业务人员审核后应用。它不替代原平台风险评估、隐患定级、整改闭环、SDS 核验或现场测绘，也不自动生成真实三维结构。

禁止输出或计算：爆炸超压、热辐射、毒气浓度、危害半径、扩散边界、经济损失、伤亡人数和真实事故结论。原风险等级只作为原记录事实展示，不能直接推断爆炸或火灾。

## 2. 问题对象分类

问题属性必须标明为以下之一：

- **人**：人员资质、培训、规程执行、劳动防护、身体精神状态、责任意识、应急处置能力、押运人员配置。
- **物**：包装、标识、货签、管道、阀门、装卸设备、检测报警仪、静电/防雷/防爆设施、消防和应急设备、通风照明、防溜隔离设施。
- **环**：站场和装卸线布局、安全距离、作业通道、地面、防渗漏、排水、照明、警示、降雨、高温和湿滑等现场环境。
- **管**：制度、许可、监督检查、交接、混装混运、数量管控、应急预案、整改复核和闭环管理。

“人、环、管”类问题默认展示作业防控、巡检、警戒、撤离、报警或整改响应；不得仅凭风险等级直接生成火灾、爆炸或气体扩散。只有“物”类问题在货物性质和触发条件均有依据时，才允许映射泄漏、逸散或受控火焰。

## 3. 输入字段

```json
{
  "source_id": "原平台评估记录 ID",
  "source_version": "原记录版本",
  "stage": "进场 / 装卸 / 搬运",
  "dimension": "人 / 物 / 环 / 管",
  "hazard_code": "危险源编号",
  "hazard_name": "危险源名称",
  "problem": "隐患或问题描述",
  "cargo": "货物名称",
  "un_number": "UN 编号",
  "material": "平台已知物料性质或 unknown",
  "measured": "检测项目、检测值、单位",
  "standard": "标准值或判定依据",
  "risk": "原风险等级",
  "status": "原整改状态",
  "action": "原整改措施"
}
```

输入中的照片仅作为证据链接，当前 AI 不分析照片，不根据照片猜测几何、物态或事故事实。

## 4. 输出 JSON

```json
{
  "summary": "审核摘要",
  "zone": "Z02 | Z03 | Z05",
  "event": "leak | dispersion | fire | explosion | control",
  "material": "unknown | flammable_liquid | flammable_gas | toxic_gas | corrosive_liquid | other",
  "problem_type": "人 | 物 | 环 | 管",
  "issue": "从隐患描述提炼的问题对象",
  "consequence": "候选后果和触发链，定性描述",
  "caption": "现场演练弹幕",
  "model_prompt": "给现有程序化铁路场景的建模提示词",
  "reasons": ["与原指标、货物、标准和状态的关联"],
  "missing": ["需要人工核实的条件"],
  "actions": ["衔接原措施和原权限的复核建议"]
}
```

### 输出规则

1. `problem_type` 必须能追溯到原平台维度或隐患目录；不确定时返回“管”并在 `missing` 说明待核实。
2. `issue` 使用短对象名，例如“危险品包装完整性”“有毒气体检测报警仪”“劳动防护与身体状态”。
3. `consequence` 描述“问题 → 可能触发 → 可能后果”，使用“可能、若、待核实”，不得写成已发生或必然发生。
4. `control` 用于巡检、警戒、响应、撤离和整改闭环展示，不显示泄漏、燃烧或爆炸粒子。
5. `leak` 只展示局部渗漏、喷漏、液池或收集隔离；`dispersion` 只展示定性气体逸散和风向示意。
6. `fire` 需要可燃液体/气体和已核实的点火条件；`explosion` 还需要明确的积聚与混合条件。缺失条件必须进入 `missing`，不得自动满足。
7. 毒性或腐蚀性不能直接当作可燃物；未知物料只能定位问题，不得虚构泄漏形态。
8. `caption` 必须是弹幕式短句，例如：`物类问题：柴油包装破损，可能发生液体泄漏！（演练假设）`。不得使用“已发生”“必然爆炸”等表述。
9. `model_prompt` 必须说明问题属性、展示对象、动画分支、响应动作和定性边界；不生成代码。
10. `actions` 只建议回到原平台补齐检测、照片、复核和整改证据，不创建隐患、不修改原风险等级、不改变整改状态。

## 5. 建模提示词模板

```text
铁路危货{problem_type}类问题建模：{issue}。
原平台问题：{problem}；危险源：{hazard_name}；环节：{stage}；货物：{cargo}；物料性质：{material}。
在{zone_name}展示{event_description}，同步显示巡检人员、警戒/隔离、报警和原措施响应。
通过文字弹幕展示：{caption}。
仅做定性演示，不计算浓度、扩散半径、超压、热辐射、伤亡或经济损失；原风险等级和整改状态保持原记录值，应用前由业务人员审核。
```

## 6. 现有程序化场景映射

- `Z02`：罐车装卸、输送管道、阀门、接地和装卸作业。
- `Z03`：包装货物站台、货位、搬运工具、通道和防渗漏。
- `Z05`：暂存交接、押运监护、应急保障、报警和整改响应。
- `leak`：液体喷溅、液池、收集隔离。
- `dispersion`：气体粒子与风向示意。
- `fire`：受控火焰与报警响应；仅在条件已核实时启用。
- `control`：人员巡检、定位、警戒和防控处置，不显示物理事故。

场景字幕同时展示 `caption` 和阶段提示；字幕是解释性信息，不代表现场已发生事故。

## 7. 审核清单

- 问题属性是否与原平台维度和隐患目录一致？
- 货物、UN、物料性质、检测值和标准是否来自原记录？
- 是否把“高风险”误写成“必然爆炸”？
- 人、环、管问题是否被正确映射为控制和响应演示？
- 物类泄漏/逸散/火焰是否有相应触发条件？
- 弹幕是否明确“可能”和“演练假设”？
- 原措施、原风险等级和整改闭环是否保持只读？
- 是否列出需要现场人员补充的条件和证据？

## 1. 改进目标

在保留现有风险评估、隐患上报、整改闭环和历史查询页面的基础上，将三维铁路场景融入平台业务。用户完成评估后，应能在场景中找到问题位置，理解问题发生的过程、可能造成的后果，以及整改应针对什么对象。

平台应形成“业务数据与评估 → 场景定位 → 过程与后果演示 → 评估资料导出 → 原流程整改与复核”的连续使用体验。三维展示要服务于问题解释和整改，不能只有火焰、爆炸等结果特效。

第一阶段优先采用通用铁路场景模板承接数据。上传一张现场图片就自动重建完整站场、为每个隐患生成专属模型、精确计算事故范围和损失，均不能作为对话中已经确定可交付的能力。

## 2. 对话内容及需求性质

| 编号 | 对话要点 | 整理结论 | 性质 |
| --- | --- | --- | --- |
| R2-01 | “导入我们平台的数据……火灾，爆炸那种动态效果” | 三维场景应支持平台评估数据带入，并提供适用的事故情景演示 | 明确提出；首批情景待选定 |
| R2-02 | “发生事故那一刻的工作场景”“过程+结果一起呈现” | 展示作业环境、问题位置、异常过程及后果，不能只显示最终结果 | 明确诉求 |
| R2-03 | “看到发生问题的位置、原因在哪，才好去整改” | 场景对象应关联问题说明、依据和整改建议；已知原因与假设原因分开 | 明确诉求；证据表达为整理补充 |
| R2-04 | “导入一张图片然后自己建模出来” | 探索图片辅助定位、分析和建模；完整自动重建能力尚未确定 | 探索性建议 |
| R2-05 | 局部照片难以建模，可先分析、分类，填表说明区域 | 允许人工填写区域、设备和后果类型，以模板映射作为可行路径 | 对话中提出的实现思路 |
| R2-06 | “先平台评估……给一个建模模版摆在中间” | 评估业务作为基础，中部三维模板用于辅助展示，避免每个问题都重新建模 | 对话后段提出的收敛方案，建议优先 |
| R2-07 | “word或者excel……参数和评估结果都写清楚” | 导出可用于汇报和后续建模的参数与评估资料 | 明确诉求；格式细节待确认 |
| R2-08 | “肯定得演示一遍……建模的过程” | 提供从数据输入到场景配置、问题演示的完整汇报流程 | 明确诉求；是否现场生成模型待确认 |

| R2-10 | “前面的闭环之前的页面也得保留……再把数字孪生整进去” | 保留并改进既有业务页面，将三维展示融入原平台 | 明确保留要求 |
| R2-11 | 专属建模由有需要的用户付费，以及商业化讨论 | 通用模板与定制建模可分层考虑；支付、订单和收费标准不进入本轮默认范围 | 商业化设想 |

原文“爆炸半价”结合语境理解为“爆炸半径”，属于整理时的文字纠正。对话只是讨论是否需要定量后果，没有确定半径算法、判据或损失计算方法。

## 3. 保留与整合范围

### 3.1 保留的业务能力

- 保留风险评估及评估前的信息填写、数据录入和导入页面。
- 保留隐患上报、整改措施、整改落实情况、现场复核、退回整改和历史记录入口。
- 保留评估结果、已有证据和报告资料，避免改造三维展示时丢失业务上下文。
- 在原业务页面内增加场景入口和关联信息，不以单独的三维演示页替代完整平台。

### 3.2 三维场景的职责

三维场景负责定位问题、解释过程和展示给定假设下的后果。评估判断、隐患确认、整改分派、复核和闭环仍由原业务模块负责。

“数字孪生”是对话中的建设方向。本阶段应按实际能力命名为“铁路三维场景 / 事故情景演示”；只有具备真实场站映射、持续数据同步及校验机制后，才能进一步说明其数字孪生能力。现有示范模板不等同于现场实时还原。

## 4. 数据带入与场景配置

### 4.1 平台数据带入

用户从已有评估或隐患记录进入场景时，应携带所属铁路局、场站或区段、作业区域、问题描述、货物与设备信息、评估结果和证据引用。导入后先预览并确认字段与场景对象的对应关系，再应用到模板。

建议第一版优先提供“从平台记录带入”，另行明确是否需要上传 Excel、JSON 等文件。文件导入属于实现建议，对话没有规定具体格式；导出的 Word/Excel 也不能默认视为可再次导入的同一模板。

### 4.2 最小场景资料

| 分组 | 建议内容 | 处理要求 |
| --- | --- | --- |
| 业务关联 | 原评估或隐患编号、记录版本、所属局站/区段 | 可回到来源记录；独立演练标明未绑定业务记录 |
| 问题定位 | 作业区域、站台/股道、设备或部件、人工标注位置 | 定位不明确时提示补充，不能任意落点 |
| 问题描述 | 异常现象、已确认原因、待核实原因、证据附件 | 假设原因与已确认事实分开显示 |
| 情景选择 | 泄漏、火灾、爆炸或其他适配情景 | 列为候选；首批支持类型需确认，不把所有问题都转为爆炸 |
| 演示参数 | 事件起点、过程阶段、适用的货物和环境参数 | 默认值标明演练假设，缺失项不自动补成现场事实 |
| 模板信息 | 模板名称、版本、对象映射、调整说明 | 保留配置结果，便于重放和报告引用 |

真实记录与模板无法准确匹配时，允许展示照片及问题标注，或者使用明确标识的近似示范区域；不能为了完成动画伪造现场布局。

## 5. 图片辅助与建模方式

### 5.1 图片辅助流程

建议采用“上传图片 → 选择或填写区域/设备 → 人工标注问题位置 → 可选 AI 辅助分析 → 人工确认 → 选择模板并映射对象”的流程。

局部照片仅说明可见部位，不能可靠推断整座站场的结构、尺度和设备布局。用户应能够在表单中补充区域、设备、异常情况以及关联记录，避免图片无法重建就阻塞业务。

AI 可辅助识别可见对象、整理描述和提出待核实线索。是否泄漏、是否会起火或爆炸、具体原因和风险等级，应结合物性、检测信息、作业条件及专业确认；不能仅凭一张照片直接确定。

### 5.2 建模分层

| 层次 | 目标 | 本轮建议 |
| --- | --- | --- |
| 通用模板配置 | 复用铁路站场、作业点、车辆和设备，配置问题对象及演示过程 | 优先建设，作为汇报演示主体 |
| 图片辅助映射 | 将照片中的已确认问题对应到模板区域或设备 | 分阶段接入，始终保留原照片与人工修正 |
| 专属场景定制 | 根据特定场站资料补建模型，表现专有设备及过程 | 作为扩展服务，单独评估资料和工作量 |
| AI 在线生成模型 | 用户在平台发起模型生成，查看任务进度并验收结果 | 技术探索；需另定输入、生成方式、耗时、失败处理和质量标准 |

对话提到“机械位置坏了、偏轨道”等不同场景，说明对象和过程需要可扩展，并未确定每类设备故障都要纳入第一版。

## 6. 问题过程与后果演示

### 6.1 演示结构

每个支持的情景应至少表达以下四个阶段：

1. **作业背景：** 显示作业区域、车辆或设备及相关环境，标明示范或真实资料来源。
2. **问题定位：** 高亮异常部位，显示问题描述和证据；原因不明时显示“待核实”。
3. **过程演示：** 按选定假设表现异常发生及发展，例如某连接部位出现泄漏。发展路径应由情景条件决定，不暗示任何泄漏都必然爆炸。
4. **结果与整改关注：** 展示适用的危害效果，并关联已有评估说明、整改措施或防控建议。

建议提供播放、暂停、重播、阶段跳转和视角聚焦，方便汇报时说明问题从哪里发生、如何发展以及为什么需要整改。事故演示与现有列车通行、人员巡检等日常动画分开控制。

### 6.2 定性展示与定量计算

| 模式 | 输出内容 | 前提与边界 |
| --- | --- | --- |
| 定性情景演示 | 泄漏、烟雾、火焰或爆炸效果，过程阶段与可能后果说明 | 明确标注“演示效果 / 非实测影响范围”，不宣称真实半径或金额 |
| 定量后果分析 | 经校核的影响范围、阈值及适用的损失估算 | 需要确认模型、输入、尺度、阈值、资产资料和校核依据；作为后续专项 |

对话没有最终选择“精确计算”还是“定性演示”。建议首版采用定性演示，保留定量结果接入位置。爆炸半径必须说明对应的后果判据，不能用一个无阈值的圆表示所有危害；经济损失缺少资产与估值依据时显示“未评估”，不能由视觉效果生成金额。

无论采用哪种模式，演示本身不得自动提高风险等级、创建正式隐患、生成巡检记录或推进整改闭环。

## 7. 隐患整改闭环调整

### 7.1 需求2对话提出的流程

**工人上报隐患 → 安全员接收并制定整改措施与意见 → 项目经理统筹资源、推动实施 → 项目经理填报整改落实情况 → 安全员现场复核、审核 → 通过后闭环；不通过则退回继续整改。**

| 角色 | 对话中提出的职责 | 应留存的业务资料（整理建议） |
| --- | --- | --- |
| 工人 | 通过平台上报隐患 | 问题描述、位置、上报人和时间、现场证据 |
| 安全员 | 接收隐患，制定措施与意见，完成现场复核和审核 | 整改意见、复核依据、结论、时间和不通过原因 |
| 项目经理 | 统筹资源，推动整改，填报落实情况并提交复核 | 实施说明、落实情况、证据、提交人和时间 |

可采用“待接收 → 待制定措施 → 整改中 → 待安全员复核 → 已闭环”的状态表达；复核不通过回到“整改中”。这是整理提出的状态建议，并非现有系统已启用的状态或已确认的数据迁移方案。

### 7.2 与原需求的差异

现有《系统需求说明书》第 8.9 节和第 10.2 节要求“安全工程师技术复核 + 项目经理管理确认”，双方均通过后销号。需求2则由项目经理先组织和填报，再由安全员最终复核通过后闭环；两者在最终确认顺序与条件上不同。

后续需明确：需求2是否替代原双人确认规则；“安全员”与“安全工程师”是否同一角色；项目经理是否就是整改提交人；是否还需要项目经理在安全员复核后进行最终确认。确认前保留现有流程，本整理稿不授权直接删改双人确认、权限或历史状态。

三维演示可以引用问题与整改资料，并提供返回原记录的入口；不得在场景页面另建一套闭环流程。这也延续原专项页“不生成隐患、不处理闭环”的边界。

## 8. 评估资料导出与汇报演示

### 8.1 Word / Excel 资料

导出资料应把参数和评估结果写清楚，便于业务汇报，也便于需要专属模型的用户向建模人员提供资料。建议包含：

- 对象与范围：局站/区段、作业区域、设备、记录编号和版本。
- 输入参数：名称、数值、单位、来源、未知项和演练假设。
- 评估结果：风险或隐患说明、等级及依据、已确认原因与待核实问题。
- 图片证据：原照片、标注位置和说明。
- 场景配置：模板版本、问题对象、情景选择、过程阶段及必要截图。
- 整改信息：措施与意见、责任角色、落实情况和复核记录，按实际记录与权限导出。
- 适用边界：是否示范、是否真实空间标定、是否完成定量计算。

Word 适合完整说明，Excel 适合结构化参数与结果清单。对话中的“Word 或 Excel”尚未确定是二选一还是两者都要；正式格式、模板和是否附带模型文件需确认。不能把普通评估资料包标成已经完成专属建模或事故计算的报告。

### 8.2 汇报演示流程

建议准备一个有完整资料的代表性铁路作业案例，依次演示：

1. 在原业务页面录入或带入数据，查看评估结果。
2. 进入中部场景，选择模板并确认区域、设备和问题位置。
3. 配置一个支持的异常情景，播放“背景—问题—过程—后果”。
4. 展示对应证据、原因说明和整改措施，返回原业务记录。
5. 预览并导出参数与评估资料。
6. 若闭环规则已确认且本轮纳入范围，再按实际角色演示上报、落实、复核及退回分支。

如果使用预制模板，应把这一过程称为“模板配置与情景演示”；如果由开发阶段 Agent 生成代码，应说明这是开发方式，不能演示成平台已经提供“在线 AI 自动建模”。

## 9. 建议优先级与验收要求

以下是根据对话的可行性整理提出的实施顺序，不是已承诺的工期。

| 优先级 | 建设范围 | 验收要点 |
| --- | --- | --- |
| P0 | 保留既有页面，明确闭环规则差异 | 原评估、上报、整改和历史入口仍可使用；形成最终闭环角色与顺序的确认记录 |
| P1 | 平台数据带入、通用模板、问题定位 | 来源记录可追溯；区域和设备映射正确；缺信息时可补录，不随机定位 |
| P1 | 一个代表性情景的过程与后果演示 | 可看到问题起点及发展阶段；可暂停、重播；清楚标明演示假设，不伪造计算数值 |
| P1 | 参数与评估资料导出、汇报链路 | 导出与当前确认数据一致，来源、单位、缺失项完整；可走通一次端到端演示 |
| P2 | 图片上传、人工标注及辅助模板映射 | 原图与标注可保存、复查；局部图片不被当作完整站场；支持人工修正 |
| P2 | 经确认的新闭环规则实施（如决定替换） | 角色权限、提交顺序、复核通过/退回及历史记录均正确；旧任务处理方式明确 |
| P3 | AI 图片分析、在线模型生成、定量后果与损失计算、专属建模服务 | 分别确定数据、算法或模型、性能、失败处理和校核标准后再立项 |

不应把全部火灾、爆炸、泄漏与设备故障情景、任意照片建模和定量计算同时作为首版演示的必备项。
